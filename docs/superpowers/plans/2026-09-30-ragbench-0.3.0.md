# RAGBench 0.3.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans. The user runs this plan **one task at a time** ("implement task N"). Read §0 and §1 first, then only your task. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Turn RAGBench from a retrieval-strategy comparer into a tool that answers *"which agentic-RAG architecture (retrieval + chunking + tools) is best for **my** documents and **my** questions — and what should I deploy?"* — with a runnable winner config as the output.

**Architecture:** Keep the evaluation-first core (`BaseRAGSystem` → `BenchmarkEvaluator` → reports). Add (a) a component registry + typed configs so approaches, chunkers, rerankers, stores, providers and tools are pluggable and self-documenting, (b) a step-trace model so multi-step/agentic systems are measurable, (c) caching + parallel execution so big comparisons are fast and cheap, (d) statistics + a recommendation engine that turns leaderboards into a decision, (e) dataset onboarding (init / synthetic questions / pooled qrels / `auto`), (f) a redesigned report and CLI.

**Tech Stack:** Python ≥3.11 (decided in Task 1), Typer, Pydantic v2, pandas/numpy, Jinja2, OpenAI SDK, optional extras (anthropic, sentence-transformers, faiss, qdrant-client, chromadb, pypdf, python-docx).

### Task 3: Evaluator resilience & retrieval-depth fix
**Model:** Opus · **Depends on:** 2 · **Risk:** changes metric semantics (intended)

**Why (verified):** (1) In `results/…/metrics_summary.csv`, `Recall@10 == Recall@5` for **every** system because each system returns only `top_k=5` chunks — so `MRR@10`/`nDCG@10`/`Recall@10` in leaderboards are really @≤5. (2) One exception in one question (`future.result()`) kills the whole paid run and loses everything. (3) Leaderboard/report columns hard-code `@5/@10`; if `k_values` omits them the UI silently shows `0.000`. (4) No run manifest (versions, git sha, seed, mode).

**Design:** separate **retrieval depth** (how many ranked chunks are scored by metrics, = `max(k_values)`) from **context size** (chunks given to the generator, = `context_k`, default 5). `BaseRAGSystem.answer_question` calls `fetch_context(question, top_k=retrieval_depth)` and passes `chunks[:context_k]` to the generator. Retrieval metrics use the full ranking.

**Files:** Modify `src/ragbench/rag_systems/base.py`, all `rag_systems/*_rag.py` (honor `top_k` as depth; `parent_doc` keeps parent semantics: depth = parents returned), `src/ragbench/config/schema.py` (`EvaluationConfig.context_k: int = 5`, `retrieval_depth: int | None = None` → default `max(k_values)`), `evaluation/evaluator.py`, `reporting/*`, `cli.py` (`_LEADERBOARD_COLUMNS` dynamic), `evaluation/retrieval_metrics.py`. Tests: `tests/test_retrieval_depth.py`, `tests/test_run_resilience.py`, update smoke tests.

**Interfaces — Produces:**
```python

class EvaluationConfig:
    context_k: int = 5

    primary_k: int | None = None             # None → 5 if 5 in k_values else median(k_values); used for leaderboard "headline" columns
```

### Task 6: Persistent caches (LLM responses, embeddings, index snapshots)
**Model:** Opus · **Depends on:** 2, 3, 4

**Why:** Iterating on a benchmark re-pays for identical LLM/embedding calls; the current embedding cache lives only in-process. A disk cache makes re-runs near-free and fast (big UX + performance win) and makes live runs resumable after crashes.

**Design:** stdlib `sqlite3` (WAL), one file `.ragbench_cache/cache.sqlite3` under the project root (configurable `cache.dir`, `RAGBENCH_CACHE_DIR`). **Files:** Create `src/ragbench/cache/{__init__,store,keys}.py`, `src/ragbench/models/cached.py` (wrappers `CachedLLM`, extend `CachedEmbeddingModel` to use disk tier), `tests/test_disk_cache.py`. ### Task 17: Agent loop + corrective RAG + iterative multi-hop
**Model:** Opus · **Depends on:** 5, 8, 15

**Why:** Despite the project goal ("agentic RAG"), **no current system loops** — all are single-pass pipelines. This task adds the reusable agent loop and the first two genuinely agentic systems.

**Design:** `AgentLoop` = bounded controller: `max_steps`, `max_cost_usd_per_question`, `max_tokens`, `stop when sufficient`; every iteration emits `Step`s; budget exhaustion returns best-effort answer flagged `budget_exhausted: true` (never raises). - `corrective` (CRAG-style): retrieve → LLM **grades** each chunk (relevant / ambiguous / irrelevant) → if insufficient: rewrite query and/or widen (`expand_to: hybrid|full_doc`) and retry up to `max_rounds` → generate → optional **groundedness self-check** (answer supported by context?) with one regeneration.
